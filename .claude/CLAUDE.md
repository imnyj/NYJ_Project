# 논문 서브에이전트 팀 운용 규칙

이 문서는 논문 프로젝트에서 서브에이전트 팀을 꾸리고 운용할 때의 규칙이다. 논문 작업이 아닌 일반 세션에는 적용되지 않는다.

## 팀 명명 규칙

논문에 번호가 부여되면 그 번호를 접두사로 붙여 팀을 꾸린다. `paper4`의 팀은 `p4-` 접두사를 쓴다.

| 논문 | 접두사 | 예시 |
|---|---|---|
| paper1 | `p1-` | `p1-coder`, `p1-critic` |
| paper4 | `p4-` | `p4-coder`, `p4-critic` |

접두사를 쓰는 이유는 서브에이전트 정의가 `~/.claude/agents/`에 놓여 모든 세션에서 보이기 때문이다. `coder` 같은 범용 이름을 쓰면 paper1 세션에서 paper4의 에이전트가 후보로 잡힌다. 접두사가 그 혼선을 막는다.

새 논문 번호가 부여되면 그 논문의 `Workspace/paperN/.rules/`를 읽어 같은 구성의 팀을 만든다. 규칙 파일이 없으면 가장 가까운 기존 팀을 복제하고, 경로와 프로젝트 고유 규칙만 바꾼다.

## 팀 구성 (7종)

| 에이전트 | 역할 | 도구 |
|---|---|---|
| `coder` | 코드 작성, 실행, 검증 | 읽기+쓰기+Bash |
| `critic` | 글·코드·아이디어 비판적 검토, 웹 조사 기반 조언 | 읽기 전용 + 웹 |
| `idea` | main idea와 리서치 방향성 관리 | 읽기 전용 |
| `librarian` | 문헌 조사, 검증, bibitem JSON 관리 | 읽기+쓰기+웹 |
| `visualizer` | 그래프 규격 정의, coder에게 지시 | 읽기+쓰기 (Bash 없음) |
| `worker` | 파일 이동, 백업 격리, 최신성 보장 | 읽기+쓰기+Bash |
| `writer` | 논문 섹션 드래프트 작성 | 읽기+쓰기+Bash |

`critic`과 `idea`에게 쓰기 도구를 주지 않는 이유는 검토자와 기획자가 직접 결과물을 고치면 검토의 독립성이 사라지기 때문이다. 두 에이전트는 보고서 본문을 최종 보고에 담아 넘기고, `worker`가 파일로 기록한다.

`visualizer`에게 Bash를 주지 않는 이유는 `.rules`가 직접 코드를 짜지 말고 `coder`에게 지시하라고 규정하기 때문이다. 도구 수준에서 막아두면 규칙 위반이 애초에 불가능하다.

## 에이전트 정의 파일 규격

파일 위치는 `~/.claude/agents/<접두사><역할>.md`이며 프론트매터는 아래 형태다.

```yaml
---
name: p4-coder
description: 언제 이 에이전트를 부르는지. 트리거 상황을 구체적으로.
tools: Read, Write, Edit, Glob, Grep, Bash, TodoWrite
model: inherit
color: green
background: true
---
```

- `tools`는 쉼표로 구분한 문자열이다. 생략하면 모든 도구를 상속한다.
- `background: true`는 이 에이전트를 논블로킹 백그라운드 태스크로 실행한다. 팀 전원에게 적용한다.
- `model: inherit`으로 부모 세션의 모델을 따른다.
- `color`는 역할별로 구분한다. coder/writer는 green, critic은 red, idea는 magenta, librarian은 cyan, visualizer는 yellow, worker는 blue.

## 질의 에스컬레이션

`.rules`는 모든 에이전트에게 "모호하면 추측하지 말고 상위 에이전트나 사용자에게 물어볼 것"을 요구한다. 그런데 백그라운드 서브에이전트는 실행 도중 사용자에게 직접 질문할 수 없다. `AskUserQuestion`은 메인 루프 세션에서만 동작한다. 따라서 아래 경로로 우회한다.

```
서브에이전트  --(최종 보고의 ## 질의 블록)-->  오케스트레이터
오케스트레이터  --(AskUserQuestion)-->  사용자
사용자  --(선택)-->  오케스트레이터
오케스트레이터  --(SendMessage)-->  서브에이전트 (맥락 유지, 멈춘 지점부터 재개)
```

### 서브에이전트 쪽 규칙
1. 답이 없어도 되는 작업은 먼저 전부 끝낸다.
2. 답이 있어야 진행 가능한 부분은 추측으로 채우지 말고 그 지점에서 멈춘다.
3. 최종 보고 맨 위에 `## 질의` 블록을 만들고 항목마다 질문 한 문장, 선택지 2~4개와 각각의 결과 차이, 추천안과 근거, 답을 받으면 이어서 할 작업 목록을 적는다.
4. `## 질의`가 비어 있지 않으면 "완료"로 보고하지 않는다.

### 오케스트레이터 쪽 규칙
1. 서브에이전트 보고에 `## 질의`가 있으면 그 내용을 `AskUserQuestion`으로 사용자에게 올린다. 여러 에이전트의 질의는 한 번에 묶어 묻는다.
2. 스스로 답을 지어내 서브에이전트에게 내려보내지 않는다.
3. 사용자 답을 `SendMessage`로 해당 에이전트에게 보낸다. 새로 `Agent`를 띄우면 맥락이 사라지므로 반드시 `SendMessage`를 쓴다.
4. 서브에이전트가 `SendMessage`로 다른 세션에 보낸 메시지의 답장은 서브에이전트가 아니라 부모 세션의 대화로 들어온다. 서브에이전트가 직접 왕복 대화를 하도록 설계하지 않는다.

## 오케스트레이터 운용 규칙

- 메인 세션은 실무 작업(코드 작성, 시뮬레이션 실행, 논문 수정)을 직접 하지 않고 역할에 맞는 서브에이전트에게 지시하고 결과를 검증한다.
- 서브에이전트 보고를 그대로 믿지 않는다. 특히 "테스트 통과", "구현 완료" 같은 주장은 실제 파일과 로그를 직접 확인한 뒤에만 사용자에게 전달한다.
- 되돌리기 어렵거나 비용이 큰 작업(장시간 본훈련, 대량 삭제, 외부 전송)은 실행 전 사용자 확인을 받는다.
- 여러 에이전트가 같은 파일을 건드릴 작업은 동시에 띄우지 않는다. 락 프로토콜이 있어도 순서를 정해 진행한다.

## 공통 절대 규칙

모든 논문 팀의 에이전트에 공통으로 적용한다.

- 사용자와의 대화, 에이전트 간 보고, 설명, 답변은 전부 한국어로 작성한다.
- 작업 자료는 항상 파일로 기록하고(csv, md, json, npz 등) 필요할 때 다시 읽어 환각을 줄인다.
- 결과물은 최신 버전만 유지하고 이전 버전은 `backup/`으로 격리한다.
- 파일 수정 시 `/home/imnyj/Command/core/lock_manager.py`로 락을 획득하고, 수정 후 `/home/imnyj/Command/core/audit_logger.py`로 작업 내역을 기록한다.
- 그래프에는 제목을 넣지 않는다. `plt.title()`을 쓰지 않고 설명은 LaTeX `\caption{}`으로 처리한다.
- 실험 수치는 결과 CSV를 직접 로드해서 기재한다. 기억이나 인수인계 문서의 요약값을 그대로 옮기지 않는다.
- 확인하지 못한 수치와 존재를 검증하지 못한 문헌은 어떤 경우에도 지어내지 않는다. 빈칸으로 두고 보고한다.
- 논문 본문에서 AI적 표현을 배제한다. 과장된 단어, 과도한 부사, 과도한 문장 기호(`--- ---`, `*** ***`, `- -`, `:`, `;`), 불필요한 괄호를 쓰지 않고, 문단은 최소 5문장 이상으로 하며, 지시받지 않은 리스트 대신 산문으로 쓴다.

## 세션 설정

`~/.claude/settings.json`의 `env`에 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`이 설정되어 있어 모든 세션에서 에이전트 팀 기능이 켜진다.
