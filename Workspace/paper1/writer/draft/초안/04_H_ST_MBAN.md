# 4. H-ST-MBAN Based Content Precaching

In this section, we detail the overall process of content precaching based on the proposed Heterogeneous Spatio-Temporal Multi-Branch Attention Network (H-ST-MBAN) and explain its architectural mechanisms. The entire content precaching framework operates through a multi-step pipeline. First, upon a content request from a vehicle, a complete feature vector is generated by aggregating localized traffic and networking parameters. Second, the generated feature vector is fed into the inference module, which predicts the vehicle's dwell time within the current and subsequent Road Side Units (RSUs). Third, using the predicted dwell times, the content precaching is executed to ensure uninterrupted content delivery. Finally, upon the completion of the vehicular scenario, the true dwell time values are collected to update the dataset, which then drives the pre-training and fine-tuning processes of the model.

## 4.1. Content Request and Feature Extraction

When a vehicle requires specific content and resides within the communication coverage of an RSU, it immediately transmits an Interest packet to request the content. If the vehicle is outside the communication range, it remains in a waiting state until it enters an RSU's coverage. The Interest packet contains important information, including the vehicle ID, content ID, vehicle position, velocity, distance to the preceding vehicle, required number of lane changes, navigation path to the next RSU, and the initial chunk number of the requested content. Upon receiving this packet, the current RSU initiates the content provisioning process in accordance with Content-Centric Networking (CCN) procedures. Concurrently, the RSU uses the received information to instantiate an entry in its Pending Data Table (PDT), using the vehicle ID and content ID as key values, and records the initial vehicular position and velocity.

At this stage, the RSU immediately appends readily available local traffic information to the PDT, which includes the current traffic light status, remaining time for the traffic light phase change, average velocity of vehicles within the communication range, and the RSU's communication radius. Furthermore, using the vehicle's position and velocity, the RSU calculates the distance to its own center point ($d_{rsu}$) and the estimated arrival time ($t_{est}$), and records them in the PDT. The movement direction of the requesting vehicle is also classified and logged: it is denoted as 1 if the vehicle has already passed the RSU located at the intersection (i.e., moving away from the RSU) and 0 if it has not yet passed (i.e., approaching the RSU). By identifying the specific lane occupied by the requesting vehicle, the RSU collects additional localized metrics, including the instantaneous and average velocities of the preceding vehicle, the number of vehicles ahead in the same lane, and the queue length and occupancy rate of the respective lane. Based on the vehicle's navigation path, the RSU further calculates and updates the PDT with the remaining travel distance within the current RSU's coverage, the distance to the entry point of the next RSU, and the distance to the exit point of the next RSU. Through a beacon message-based average vehicle velocity management mechanism, the RSU also estimates the number of vehicles currently residing in its communication range that have not yet been explicitly aggregated, thereby refining the data in the PDT.

To acquire additional predictive information from the subsequent RSU along the vehicle's path, the current RSU transmits an `[INFO REQ]` packet. This packet contains the current RSU ID, vehicle ID, and content ID. Upon receiving the `[INFO REQ]` packet, the next RSU registers the request in its Pending Request Table. Following this, the next RSU updates the packet's source ID with its own ID and broadcasts it to its neighboring RSUs in the form of an `[INFO HELLO]` packet. The neighboring RSUs, upon receiving the `[INFO HELLO]` packet, consult their average velocity management tables to aggregate the number of vehicles destined for the next RSU that are expected to enter or merge into the target path from adjacent intersections ($n_{merge,nxt}$). These neighboring RSUs then reply to the next RSU via an `[INFO REP]` packet containing this merged vehicle count, along with the requesting vehicle ID and content ID. Simultaneously, the next RSU independently computes its own local parameters, including the traffic light status, remaining time for the phase change, average vehicle velocity, the queue length and occupancy rate of the lane corresponding to the requesting vehicle's entry direction, and the number of preceding vehicles already present on that specific path ($n_{ahead,nxt}$). Then, the next RSU consolidates the received $n_{merge,nxt}$ values from its neighbors and transmits a final `[INFO REP]` packet back to the original requesting RSU, using the initial RSU ID stored in its Pending Request Table as the destination. Consequently, the final `[INFO REP]` packet received by the initial RSU contains a complete set of predictive metrics for the next RSU: its average vehicle velocity, the number of vehicles within its communication range, the traffic light status, the remaining time for the phase change, the number of preceding vehicles on the target path ($n_{ahead,nxt}$), and the anticipated number of merging vehicles from neighboring intersections ($n_{merge,nxt}$). The initial RSU merges this incoming `[INFO REP]` packet data into the PDT, using the vehicle ID and content ID as keys, thereby finalizing the extraction of the features.

The categorization of individual elements improves the efficiency of reflecting distinct data distributions in the next neural network model. Ultimately, by performing localized information aggregation without relying on a centralized server, this mechanism reduces server bottleneck issues and supports scalable architecture.

## 4.2. Inference and Model Architecture

The inference module predicts the dwell times for the current and subsequent RSUs, denoted as $t_{cur, dw}$ and $t_{nxt, dw}$. In the absence of a pre-trained model during the initial deployment, a cold-start heuristic mechanism calculates the dwell time mathematically by dividing the remaining travel distance by the average velocity of vehicles within the coverage. During this phase, the system maintains the data collection process to construct the dataset. Once the pre-trained H-ST-MBAN model is deployed, it conducts precise inference. Vehicular network data exhibits heterogeneous scales across kinematic, topological, and spatial properties, accompanied by frequent outliers such as sudden congestion. To prevent gradient explosion and catastrophic forgetting during online fine-tuning, the H-ST-MBAN operates through four specialized modules.

The first module handles heterogeneous feature extraction via pre-activation residual blocks. Rather than concatenating the kinematic, topological, and spatial features into a single vector, the architecture processes each domain through independent encoding networks. This late fusion structure prevents features with larger numerical scales from dominating the training process. The module applies a pre-activation residual block structure, operating in the sequence of batch normalization, rectified linear unit, and linear layer. By performing normalization before the linear transformation, this configuration mitigates gradient vanishing issues caused by heterogeneous data scales. Consequently, the input variables are projected into a unified latent space dimension, denoted as $d_{model}$.

The second module executes domain-level multi-head attention fusion. The independently encoded kinematic, topological, and spatial domains are formatted as a sequence of three distinct tokens. These tokens are fed into a multi-head attention block. This module calculates the interdependencies among the domains. It evaluates how the topological constraints, such as traffic light states, interact with the spatial vehicle density and the kinematic velocity. By utilizing attention scores, the model derives a fused representation that reflects the physical context of vehicular movement. This token-based fusion extracts the correlation between different traffic parameters without relying on simple feature concatenation.

The third module performs deterministic decoding. The fused vector from the attention block is flattened and processed through a multi-layered residual block decoder to map the latent representation to the final dwell time values, $t_{cur, dw}$ and $t_{nxt, dw}$. The system requires point-estimate values rather than probability distributions to schedule the content precaching process without latency. During model optimization, the mean absolute error, or L1 loss, is adopted instead of the mean squared error. This loss function prevents the gradients from being heavily distorted when extreme outliers occur, such as sensor noise or abrupt traffic accidents. This ensures stable convergence under highly volatile road conditions.

The fourth module applies adaptive residual prior learning through a hybrid gating mechanism. The final prediction combines the output of a tree-based machine learning model and the deep neural network. The combination is formulated as $\alpha \times \text{ML\_Pred} + \beta \times \text{NN\_Pred}$. The variables $\alpha$ and $\beta$ are designed as learnable parameters updated through backpropagation. In the initial stage, the model heavily relies on the machine learning prediction as a structural anchor to prevent divergence. As the system accumulates local data, it autonomously increases the weight of the neural network output. This adaptive gating mechanism prevents catastrophic forgetting during the real-time online fine-tuning process at the edge nodes.

## 4.3. Precaching Scheduling

Once the dwell time $t_{cur, dw}$ is obtained either via the prediction model or the heuristic approach, the current RSU ($R_{cur}$) determines the volume of content that can be transmitted. This calculation incorporates the average communication bandwidth ($B_{avg}^{cur}$) and an adaptive safety factor ($\eta$) designed to adjust for the time-varying channel characteristics. The adaptive safety factor is formulated as $\eta(t) = \alpha \cdot \bar{P}_{success}(t) - \beta \cdot f(\sigma_{channel}^2(t))$, where $\bar{P}_{success}(t)$ represents the recent average packet delivery success rate, and $\sigma_{channel}^2(t)$ denotes the variance of the channel signal-to-noise ratio. By adjusting the transmission margins according to these parameters, the system reduces the effect of channel fluctuations. The total number of chunks that $R_{cur}$ can transmit is then calculated as $N_{cur, chunk} = \lfloor \frac{\eta \cdot B_{avg}^{cur} \cdot t_{cur, dw}}{S_{chunk}} \rfloor$. Here, the chunk size ($S_{chunk}$) is fixed for all content segments. This uniformity in chunk sizing is justified by the characteristics of Content-Centric Networking (CCN), as it prevents memory fragmentation within the router's Content Store, thereby maintaining $O(1)$ cache management efficiency, and avoids packet fragmentation caused by lower-layer Maximum Transmission Unit (MTU) limitations.

Based on the computed $N_{cur, chunk}$ and the requested initial chunk number, $R_{cur}$ identifies the sequence number of the final chunk that can be delivered during the vehicle's residency in its coverage. Following this, $R_{cur}$ transmits a Precache Packet to the next scheduled RSU ($R_{nxt}$). This control packet contains the content ID, the sequence number of the next chunk to be requested, and the predicted dwell time for the next RSU ($t_{nxt, dw}$). Upon receiving the Precache Packet, $R_{nxt}$ performs a similar calculation using $t_{nxt, dw}$ to determine the volume of chunks it must prepare, and initiates the precaching process by issuing Interest packets according to standard CCN protocols. To address exceptional scenarios such as sudden vehicle route deviations, a Time-To-Live (TTL) based eviction policy is applied to all precached chunks. This policy guarantees that unrequested precached chunks are evicted, preventing the exhaustion of the Pending Interest Table (PIT) and avoiding decisions based on stale data.

## 4.4. Result Reporting

As the requesting vehicle exits the communication coverage of the current RSU ($R_{cur}$), it records the identification number of $R_{cur}$ along with the measured dwell time, $t_{cur, dw}$. During its journey toward the subsequent destination, the vehicle transmits Interest packets to attempt further content downloads according to the established protocol. Upon entering the communication range of the next RSU ($R_{nxt}$), the vehicle transmits its Interest packet to this RSU. This connection triggers the initiation of an independent content provisioning process at $R_{nxt}$, which mirrors the initial feature extraction and prediction steps described in the previous subsections. Concurrently, the vehicle activates an internal timer to measure its dwell time within the coverage of $R_{nxt}$, denoted as $t_{nxt, dw}$. Because $R_{nxt}$ has already executed the precaching scheduling, the vehicle receives the prepared content chunks without experiencing latency. In cases where specific chunks were not precached due to prediction inaccuracies, the vehicle retrieves the missing data from neighboring RSUs or the central content server through standard Content-Centric Networking (CCN) procedures.

Subsequently, as the vehicle prepares to leave the communication area of $R_{nxt}$, it stops the internal timer to record $t_{nxt, dw}$. At this point, the vehicle generates a Report packet intended to deliver the collected ground truth values back to the infrastructure. This Report packet contains the vehicle identification number, the content identification number, the previously recorded ID of $R_{cur}$, and the measured dwell times for both RSUs, represented as $t_{cur, dw}$ and $t_{nxt, dw}$. The vehicle transmits this Report packet to the connected RSU. Upon receiving the packet, this RSU inspects the target destination ID enclosed within the packet header. If the inspected target ID does not match its own identifier, the RSU acts as a relay node and forwards the Report packet through the backbone network toward the original $R_{cur}$. When $R_{cur}$ receives the forwarded Report packet, it searches its internal Pending Data Table (PDT) to locate the entry that matches both the vehicle ID and the content ID. Once the correct entry is found, $R_{cur}$ extracts the previously constructed feature vector and binds it together with the received true values of $t_{cur, dw}$ and $t_{nxt, dw}$. This binding process produces a ground truth data sample, which is then accumulated into the local dataset queue residing within the memory of $R_{cur}$.

## 4.5. Online Training

The online training process of the proposed framework operates through a five-step learning cycle designed to manage computational resources and model adaptability. The cycle begins as each Road Side Unit gathers streaming traffic data until a sufficient dataset is accumulated for training. In the initial state when no prior model exists on the edge devices, this collected data is transmitted directly to the designated local server. This data transfer is necessary because training a model from scratch requires high computational power that exceeds the typical capacity of edge nodes. Delegating this heavy workload to the local server prevents the resource depletion of individual Road Side Units and ensures stable system operation.

When the local server accumulates enough data from the connected nodes, it performs pre-training to establish a foundational model. This pre-training utilizes the aggregated data to learn general traffic patterns across the covered area. Upon completion of the training process, the local server distributes the pre-trained model to all Road Side Units under its jurisdiction. From that point onward, each Road Side Unit conducts fine-tuning independently using the provided model whenever new local datasets are sufficiently accumulated. This independent fine-tuning method reduces communication overhead by keeping new data local and provides better adaptability to specific environmental changes and concept drift.
