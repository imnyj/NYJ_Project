# 회귀 테스트 변이 검사 — src/baselines/ + heuristic_scheduler.py

작성 2026-09-01. 담당 p4-coder(baselines). Python `/home/imnyj/venv/bin/python`.

## 왜 했는가

`fix-core`가 `hot_swap()`의 NaN 가드 경합을 고치면서, 처음 쓴 동시성 테스트 2건이
**락을 제거해도 통과했다**는 것을 발견했다. GIL과 짧은 update 창 때문에 문제의
인터리빙이 사실상 샘플링되지 않았기 때문이다. 결함 유무와 무관하게 통과하는 테스트는
아무것도 증명하지 않는다.

같은 기준을 내 회귀 테스트에도 적용했다. "결함을 다시 넣으면 해당 테스트가 실제로
실패하는가"를 확인하지 않은 회귀 테스트는 회귀 테스트가 아니다.

## 방법

프로덕션 트리를 **수정하지 않았다**. 다른 에이전트가 동시에 전체 스위트를 돌리고 있어서
파일을 잠깐이라도 되돌리면 그쪽에 가짜 실패가 보인다. 대신 런타임 몽키패치로 결함
구현을 되돌려놓고 판정식만 다시 계산했다.

## 결과 — 7건 전부 탐지 성공

| 검사 | 수정본 | 결함 재주입 시 | 판정 |
|---|---|---|---|
| C-1 SPAM-D3QN 왕복 (선형 역변환 재주입) | 128/128 정확 | **32/128 정확** | PASS |
| C-3 gamma 실효 (배치 `discount` 우선 재주입) | 9/9 모델에서 gamma가 가중치를 바꿈 | **0/9** | PASS |
| 대조: 동일 gamma | diff = 0 (정확히) | — | PASS |
| H-4 `value_coef` 신호 | 동일 계수 diff = 0 | 상이 계수 diff = 1.49e-08 | PASS |
| I-HAMAPPO N=1 위험 | 비가드 `std()` → **nan** | 가드 경로는 중심화만 | PASS |
| H-2 버퍼 등록 | `epsilon`/`per_beta`/`total_updates` 전부 `named_buffers()`에 존재 | — | PASS |

C-1 재주입 시 32/128은 critic이 원래 보고한 96/128 오복구와 정확히 일치한다
(128 - 96 = 32). 즉 탐지기가 원 결함을 그대로 재현한다.

C-3의 대조군이 중요하다. "동일 gamma면 diff가 정확히 0"이 성립해야 9종에서 관측된
diff > 0 이 gamma에서 온 신호이지 비결정성 잡음이 아님이 증명된다. 같은 논리로
`value_coef`도 동일 계수에서 diff = 0 을 확인했다.

## 2차 감사 — 덮여 있던 공백 1건

`fix-core`가 자기 C2에서 "통과하는 다른 테스트가 여러 개 있어서 덮여 있는 줄 알았는데
정작 핵심 주장에는 테스트가 없었다"를 발견했다. 같은 기준으로 내 수정 9건을 다시
훑었더니 H-3에서 같은 패턴이 나왔다.

`test_sb3_baselines_accept_a_hidden_width`는 파라미터 수가 **움직인다는 것만** 본다.
`hidden_dim`이 엉뚱한 폭을 만들어도 통과하고, `apply_hidden_dim`의 docstring이 명시한
두 계약 — 명시적 `net_arch`가 우선한다, 호출자의 dict를 변형하지 않는다 — 은 **한 번도
검사되지 않았다.** 셋 다 실제로는 성립하고 있었지만, 성립을 확인한 테스트가 없으면
다음 수정에서 깨져도 아무도 모른다.

`TestHiddenDimContract` 8건을 신설했다: None 통과, 스칼라 → `[h, h]`, 명시적 `net_arch`
우선, 호출자 dict 무변형, 그리고 3종 각각에서 첫 가중치 행렬이 실제로
`(hidden_dim, STATE_DIM)`인지와 명시적 `net_arch`가 종단 간에 이기는지.

변이 검사도 같이 했다. 가장 그럴듯한 오구현(`kw["net_arch"] = [h, h]`로 무조건 덮어쓰며
호출자 dict를 그대로 변형)을 넣으면 두 계약 테스트가 전부 잡아낸다.

## 남은 사각지대

`test_deterministic_action_ignores_exploration_state`(9종)와
`test_annealing_state_survives_a_hot_swap`(9종)은 변이 검사를 하지 않았다. 전자는
결함을 인위적으로 만들려면 각 모델의 `select_action`을 고쳐 써야 한다.

후자에 대해서는 `fix-core`의 지적으로 전제를 정정한다. 내가 "순차 결정론적 복사라
경합이 없다"고 적은 것은 **그의 `hot_swap()` 수정 이후에 비로소 참이다.** 그 전에는
`validate_weights()`가 락 밖에서 돌았고, 내 H-2로 어닐링 스칼라가 `register_buffer`가
되면서 복사 대상에 들어가 창이 오히려 넓어져 있었다. 지금은 검증과 복사가
`update_lock` 아래 한 임계 구역이므로 그 테스트가 모델링하는 순차 복사가 실제 동작과
일치한다. 즉 이 테스트의 타당성은 `hot_swap_trainer.py`의 락 수정에 의존한다.

## 방법론 메모

몽키패치로 충실하게 되돌릴 수 없는 결함이 있다 — 함수 경계가 없는 인라인 비교식 같은
것. 그 경우 `fix-core`가 쓴 방식(저장소를 scratchpad로 복사해 격리된 사본에서만 소스를
고쳐 검사)을 쓴다. 내 수정 9건은 전부 메서드 경계에 있어 몽키패치로 충분했다.
