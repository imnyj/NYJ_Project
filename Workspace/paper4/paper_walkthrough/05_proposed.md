# 5단계. 제안 방안의 개발

## 목적

비교 방안의 성능과 시뮬레이션이 이미 있으므로, 이 단계에서는 제안 방안의 설계에 집중합니다. 패킷 전달 방식처럼 ML 이 아닌 부분의 방안이어도
지시만 명확하면 같은 방식으로 진행할 수 있습니다. 더 좋은 방안을 찾기 어려운 구조라면 새 아이디어만 찾으며 두 달씩 걸리기도 하지만,
그래도 결국에는 비교 방안의 성능을 넘는 제안 방안을 찾게 됩니다.

## 들어가기 전 조건

- 4단계에서 모든 비교 방안의 성능 CSV 와 수렴 모델을 확보했습니다.

## 참여 역할

coder(설계와 실험), critic(비교의 공정성 검증), idea(시도 판단과 아이디어 갱신안), worker(기록), visualizer(비교 그래프 규격)

## 절차

1. 기존 코드는 반드시 살립니다. 비교 방안의 성능은 기존 코드로 뽑은 것을 그대로 쓰므로, 제안 방안은 새 파일로 작성합니다. 기존 파일을 고쳐야 하면 먼저 사용자에게 알리고 백업을 남깁니다.
2. **[사용자 결정]** 넘어야 할 지표와 기준을 정합니다(예: R2 Score, reward, Delay, Traffic, 또는 "모든 지표").
3. 시도 방향을 넓게 잡습니다. "다양한 방법으로 최적의 방안을 찾아 달라" 고만 하면 AI 는 2024년 수준의 단순한 방안(PPO 에 무엇을 붙이는 식)부터 고려합니다.
   2026년 기준으로는 TD3, SAC, MAPPO 같은 방안이 이미 있고, 적어도 PPO 보다는 SAC 가 성능이 잘 나옵니다. 그래서 아래 같은 예시를 함께 건넵니다.
   - 내부 네트워크에 ResNet 이나 ResBlock 을 넣어 본다
   - CVAE 구조를 넣어 본다
   - MoE, Dueling 같은 구조를 조합해 본다
   - feature 를 더 세분해 범주화해 본다
   **[사용자 결정]** 시도 방향의 우선순위를 확인받습니다.
4. 시도마다 HPO 를 반드시 합니다. 하이퍼파라미터를 맞추지 않은 시도끼리 비교하면 구조의 우열을 판단할 수 없기 때문입니다.
5. 시도마다 coder 가 결과 수치를 `data/proposed/attempts.csv` 에 저장합니다. idea 가 구조, 하이퍼파라미터, 결과, 판단을 정리한 보고서를 내면 worker 가
   `idea/attempts.md` 에 한 항목씩 기록합니다.
   비교 방안의 `metrics.csv` 와 같은 지표, 같은 조건으로 비교합니다.
6. **[사용자 결정]** 탐색이 길어지면 멈출 시점이나 방향 전환을 사용자에게 묻습니다. 기준을 넘는 방안을 찾으면 critic 이 CSV 를 직접 읽어 비교의 공정성을 검증한 뒤 사용자에게 보고합니다.
7. **[사용자 결정]** critic 의 검증을 거친 최종 제안 방안을 확정합니다. 논문 전체가 이 선택에 달려 있으므로 후보가 여럿이면 후보별 성능과 특징을 함께 보여 줍니다.

## 산출물

- 제안 방안 코드(새 파일), `idea/attempts.md`, `data/proposed/attempts.csv`
- 최종 제안 방안의 최적 하이퍼파라미터, 수렴 모델, 학습 곡선 CSV, 성능 CSV

## 완료 조건

- 사용자가 정한 지표에서 제안 방안이 HPO 를 거친 모든 비교 방안을 넘었고, critic 이 같은 조건의 비교임을 확인했습니다.

## 되돌아가기 조건

- 7단계에서 제안 방안의 성능이 기대에 못 미치면 이 단계로 돌아옵니다.

## 사용자 명령 예시

> /goal baselines 의 저장된 성능(R2 score, reward, delay, Traffic 등 사용자가 지정해줄 것. 또는 "모든" 이라는 표현도 가능)을 뛰어넘는 제안 방안을 설계해야 해.
> 따라서, 내부 네트워크에 ResNet 을 심어본다던지, ResBlock 을 심어본다던지, CVAE 구조를 심는다던지, feature 를 더 categorize 해본다던지 다양한 시도를 하여 찾도록 해.
> 단, 비교를 위해서는 각 시도마다 HPO 는 필수로 하도록 해.
