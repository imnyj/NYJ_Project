# 8단계. 원고 작성과 마무리

## 목적

지금까지의 결과로 논문 원고를 씁니다. 통신 분야 논문이므로 설명이 ML 에 치우치지 않도록 프로토콜과 신호의 흐름을 중심에 두고,
서론에서 밝힌 Contributions 가 논문 전체에서 드러나도록 흐름을 맞춥니다. 섹션별 작성 요령은 사용자의 `NYJ_Paper_Prompt.md` 8장과
`/home/imnyj/command.md` 의 "논문 작성 요령" 을 합친 것입니다.

## 들어가기 전 조건

- 7단계 완료 조건을 통과했고, `contributions.md`, `intro.md`, `figure_list.md`, `librarian/references.json`, 결과 CSV 와 그래프가 있습니다.

## 참여 역할

writer(초안), critic(원고 검토), librarian(인용 추가와 검증), visualizer(그림 규격), worker(파일 정리)

## 공통 규칙 (writer 규칙 파일과 `academic-writing-style` 스킬)

- LaTeX 형식으로 섹션별 초안을 쓰고 학술 문체를 유지합니다.
- 작업 자료는 항상 파일(csv, md, npz 등)로 기록하고, 필요할 때 다시 읽어 환각을 줄입니다. 원고는 최신본만 유지하며, 이전 판을 고칠 때는 파일 락과 백업 절차를 지킵니다.
- AI 적 표현을 쓰지 않습니다.
  - 과장된 단어와 과도한 부사를 쓰지 않습니다.
  - 과도한 문장 기호(`--- ---`, `*** ***`, `- -`, `:`, `;`, 작은따옴표, 큰따옴표 등)를 쓰지 않습니다.
  - 불필요한 괄호를 쓰지 않습니다. 소괄호는 약어를 처음 설명할 때 한 번이면 충분합니다.
- 문단은 최소 5문장 이상으로 씁니다. 다만 "5문장 이상" 이라고만 지시하면 정말 5문장으로만 문단을 짜므로, 내용에 맞게 충분히 설명합니다.
- itemize 와 enumerate 는 지시받은 곳에서만 쓰고, 나머지는 산문으로 풀어 씁니다.
- 위의 문단 길이와 리스트 규칙은 서론의 Contributions 문단에만 예외를 둡니다.
- 수치는 결과 CSV 를 직접 읽어 씁니다. 인용은 `references.json` 에서 검증된 문헌만 씁니다.

## 섹션별 작성 요령

### 1. Introduction

- 3~4개 문단으로 쓰고, 문단마다 5문장 이상의 충분한 설명과 인용을 담습니다. 서론 전체에서 최소 6편 이상을 인용합니다.
- 제안 방안의 Contributions 만 예외로 itemize 를 써서 간결하게 정리합니다.
- 서론은 아래 여섯 요소를 이 순서로 담습니다. 6단계에서 승인받은 `intro.md` 의 문장 설계를 따르며, 사용자는 서론만큼은 문장 단위 설계를 직접 하는 편을 선호합니다.

| 요소 | 담을 내용 |
|---|---|
| 배경 및 동기 (Background & Motivation) | 대상 도메인(예: 자율주행, 차량 네트워크)의 발전과, 그로 인해 생기는 치명적인 문제(예: 데이터 트래픽 폭증, 지연 시간)를 제시한다 |
| 기존 해결책 (Conventional Solutions) | 이 문제를 풀려고 등장한 기본 기술(예: 엣지 캐싱, 정적 프리캐싱)을 소개한다 |
| 고도화된 해결책과 한계점 (Advanced Solutions & Limitations) | 머신러닝 등을 도입한 최신 기술을 소개하되, 현실적인 한계(예: 과도한 통신 오버헤드, 결정론적 예측으로 인한 낭비)를 분명히 지적해 연구의 필요성을 강조한다 |
| 제안 방안 (Proposed Scheme) | 지적한 한계를 넘기 위한 이 연구의 핵심 아이디어(예: 불확실성을 고려한 ST-CVAE, 분산 학습, 스냅샷 기반 데이터 수집)를 제시한다 |
| 주요 기여도 (Main Contributions) | 제안 방안의 새로운 부분을 4~5개 항목으로 요약한다(예: 데이터 수집 효율성, 모델 구조의 독창성, 학습 아키텍처, 통신 프로토콜 설계) |
| 논문 구성 (Organization) | 2장부터 결론까지의 구조를 간략히 서술한다 |

### 2. Related Works

- 단순한 논문 나열이 아니라 기술의 발전 흐름을 보여 주고 제안 방안과의 차별성을 드러내는 것이 목적입니다. 리스트를 쓰지 않고 산문으로 풀어 씁니다.
- 기술의 발전 흐름: 초기의 휴리스틱이나 정적 방식에서 시작해 점차 머신러닝(RL, FL, Transformer 등)을 적용하는 방향으로 연구가 어떻게 진화했는지 서술합니다.
- 비교 분석과 한계 지적: 최신 연구가 어떤 부분에서 성과를 냈지만, 통신 오버헤드나 예측의 불확실성 같은 측면에서 여전히 한계가 있음을 논증합니다.
- 비교 표는 반드시 넣습니다. 기존 연구와 이 연구를 한눈에 비교해, 제안 방안이 어떤 지점에서 차별화되는지 표로 직관적으로 보입니다.
  - 열 예시: Paper, ML Technique, Key Feature(예: Precaching Type), Mobility Prediction 여부, Short Description / Contributions
  - Paper 열에는 `\cite{}` 로 논문의 ID 만 넣습니다.
  - **[사용자 결정]** Key Feature 와 Mobility Prediction 처럼 주제에 따라 달라지는 열을 이 논문에 맞게 정합니다.

### 3. Network Model

- 제안 방안의 특성에 맞춰 시스템 환경과 모듈을 구성하되, 반드시 통신의 흐름을 중심으로 서술합니다. 본문에 들어가기 전에 필요한 사전 지식을 모두 설명하는 곳입니다.
- 네트워크 환경과 스킴 오버뷰(개요도 포함)는 반드시 넣습니다. 어떤 환경의 어떤 시나리오에서 어떤 노드가 어떤 동작을 하는지 확실히 알려야 하기 때문입니다.
  상태 추적 및 관리 모듈과 콘텐츠 요청 및 전달 프로토콜은 예시이므로 제안 방안에 맞게 넣거나 바꿉니다.
  - 네트워크 환경(Network Environment): 인프라를 이루는 노드(예: 차량, RSU, 콘텐츠 서버)와 통신 매체(예: 802.11p WAVE, 유선 백홀)를 정의합니다.
  - 상태 추적 및 관리 모듈(State Monitoring Modules): 어떤 노드가(예: RSU) 어떤 정보를(예: 차량의 진입과 진출 시간) 이용해 어떻게 연산하며(예: sliding window, queue)
    어떤 결과값을 도출하는지 구체적으로 적습니다. 예를 들어 평균 차량 속도(vₐᵥ)나, 통신 처리량을 기록하고 주기적으로 갱신해 얻는 평균 통신 속도(Cₐᵥ)가 여기에 해당합니다.
  - 콘텐츠 요청 및 전달 프로토콜(Content Request Protocol): 정보 교환 방식(예: CCN 기반의 Interest 패킷과 Data 패킷)을 정의하고, CS(Content Store), PIT, FIB 같은
    자료구조로 요청이 어떻게 전달되고 응답이 돌아오는지 패킷 단위로 적습니다.
  - 스킴 오버뷰(Scheme Overview): 도식과 함께 통신의 전 과정을 단계별로 서술합니다. 기본 흐름은 콘텐츠 요청, 주변 노드와의 정보 교환, ML 추론과 의사결정,
    다음 노드로의 지시(Instruction) 전달, 결과 피드백과 로컬 학습의 순서입니다. 개요도는 visualizer 에게 그림 규격을 요청해 만듭니다.
- MDP 는 이 섹션이나 본문 가운데 흐름에 맞는 곳에서 정의합니다.

### 4. 본문(제안 방안)

- 가장 중요한 규칙은 ML 모델의 구조와 연산을 통신 과정 위에 자연스럽게 녹여 내는 것입니다. 인공지능 모델의 수학적 아키텍처만 나열하지 않습니다.
- 주체와 변수를 분명히 합니다. 연산을 수행하는 주체가 누구인지(예: 현재 차량이 접속 중인 RSU) 밝히고, 입력 변수가 어떤 통신 패킷을 통해, 어떤 주기로, 누구로부터 수집되는지
  적습니다(예: 차량이 보내는 Request 패킷에 담긴 현재 속도 v_req).
- ML 아키텍처를 통신의 맥락에 둡니다. 수집한 데이터로 모델(예: ST-CVAE, MDP)이 어떻게 연산하는지 설명하고, 모델의 출력값이 무엇이며 그 값이 어떤 패킷(예: Precaching Instruction)에
  담겨 누구에게 전달되고 받는 쪽이 어떤 동작을 하는지까지 한 바퀴의 흐름을 완성합니다.
- 강화 학습이나 최적화 기법이 제안 방안이면 State, Action, Reward 가 네트워크의 어떤 통신 변수와 대응하는지 분명히 풀어 씁니다.
- 크게 보면 서론의 Contributions 가 드러나는 흐름이어야 합니다.

### 5. Performance Evaluation

1. 시뮬레이션 환경과 dataset: 다른 사람이 그대로 구현할 수 있을 정도로 구체적으로 적습니다.
   - 각 노드(RSU, 기지국, 차량 등)의 물리적 위치와 이동을 어떻게 구현했는지
   - 각 노드의 통신(유선은 어떤 표준, 무선은 어떤 표준을 썼고 어떤 특징을 반영했는지)
   - 노드 사이의 상호 작용과 환경에 대한 추가 설명
   - 학습에 쓴 dataset
2. 비교 방안: 어떤 비교 방안이 있고 어떤 논문에서 인용했는지, 어떻게 구현했는지 밝히며 구현에 쓴 GitHub 주소를 인용합니다.
3. 평가 지표: 지표마다 무엇을 뜻하는지 설명합니다(예: Access delay 는 RSU 가 서버까지 패킷을 보내 content 를 받아 오는 지연으로, 서버 접근이 얼마나 잦았는지 또는 얼마나 절약했는지를 보여 준다).
4. 결과 해석: `figure_list.md` 의 순서(7단계의 세 묶음 순서)대로 결과를 하나씩 해석하고 설명합니다.

### 6. Conclusion 과 Abstract

- 논문의 내용이 잘 드러나도록 Claude 가 판단해 씁니다. Abstract 는 대상 저널의 분량 제약에 맞춥니다.
- Abstract 끝에 "The source code of <모델 이름> is available at https://github.com/imnyj/<저장소 이름>." 문장을 넣습니다. 저장소에는 모든 것을 담을 필요는 없지만,
  적어도 제안 방안의 핵심 모델 설계는 들어가 있어야 독자가 이해하고 재현할 수 있습니다.

## 절차

1. **[사용자 결정]** 작성 플랫폼과 대상 저널, 분량 제약을 확인합니다. 기본은 Overleaf 의 LaTeX 형식이며, 이를 알려 주면 그 형식으로 씁니다.
2. writer 가 위 요령에 따라 Introduction, Related Works, Network Model, 본문, Performance Evaluation, Conclusion 과 Abstract 순서로 초안을 씁니다.
   알맞은 위치에 적절한 논문을 인용하고, 인용한 논문을 Reference 에 추가합니다. 새로 인용할 논문이 필요하면 librarian 이 2단계 검색 규칙으로 찾아 검증합니다.
   Abstract 끝의 코드 공개 문장은 저장소 이름이 정해질 때까지 `<저장소 이름>` 자리표시자로 두고, 절차 4에서 정한 뒤 채웁니다.
3. 섹션마다 critic 이 아래 항목을 검토하고, writer 가 "더 고칠 것 없음" 판정을 받을 때까지 고칩니다. 검토 보고서는 worker 가 `review/` 에 기록합니다.
   - 공통 규칙(문체, 문단 길이, 리스트, 기호, 괄호)
   - 섹션별 작성 요령(서론의 여섯 요소와 인용 수, Related Works 비교 표, Network Model 의 스킴 오버뷰와 개요도, 본문의 주체와 변수와 패킷 흐름)
   - 수치와 CSV 의 일치, 인용과 `references.json` 의 일치
4. **[사용자 결정]** 코드 공개 범위와 저장소 이름을 확인받습니다. 저장소 공개는 외부 공개이므로 실행 전에 승인을 받습니다.
5. 마무리: 모든 글이 tex 파일로 완성되면 사용자가 Overleaf 로 옮겨 컴파일 오류를 해결합니다. **[사용자 결정]** Authors, Affiliations, Funding 정보를 받아 넣습니다.

## 사용자 명령 예시

> Overleaf 의 LaTeX 형식으로 서론부터 쓸 거야. intro.md 의 문장 설계를 따르고, 배경 및 동기, 기존 해결책, 고도화된 해결책과 한계점, 제안 방안, 주요 기여도, 논문 구성 순서로 3~4문단을 써.
> 인용은 references.json 에서 6편 이상 하고, Contribution 문단만 itemize 를 써.

> Related Works 는 산문으로 쓰되 비교 표를 꼭 넣어. 열은 Paper(\cite 만), ML Technique, Key Feature, Mobility Prediction 여부, Short Description 으로 해.
