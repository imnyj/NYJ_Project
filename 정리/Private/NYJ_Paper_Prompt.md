## Paper Work

## 0. 사전 작업
Claude, CodeX, Antigravity 등을 CLI나 App으로 설치한다.
세션에서 모두 작업할 것이 아니라 subagent들로 팀을 이뤄서 작업을 하라고 하는 것이 좋다.

저자는 subagent를 7개만 둔다. 너무 많으면 오히려 협업하며 방향이 중구난방으로 설정될 수 있다:
 (1) coder:
    - 작업을 함에 있어서 자료를 항상 기록(csv, md, npz 등)하며 필요한 경우에 read하여 환각을 방지.
    - code 디렉토리에서만 작업하기.
    - 데이터를 data 디렉토리에만 쌓기.
    - 코드 완성 후 critic에게 항상 검토 받을 것.
 (2) critic: 비평가로서 coder나 writer에게 받은 결과물에 대한 수정 필요한 사항을 집요하게 추적하고 수정하라고 한다.
 (3) idea: 논문의 제안 방안 Idea에 대한 버전 또는 변경을 관리하고 저장한다.
 (4) librarian:
    - 찾은 논문의 데이터셋 메타데이터 및 참고 자료의 출처 및 요약본을 수집하고 인덱싱하며 JSON 파일로 관리하고 저장할 것.
    - 1초에 1건만 검색하며, 5시간 이상의 대기 시간이 걸리면 1분 후 재시도를 최대 5번까지 해볼것.
    - Scopus, MDPI, arXiv 등에서의 검색을 금지하고, IEEE, ACM, Elservier, ScienceDirect 등의 저명한 논문만 검색할 것.
    - 오늘 날짜 기준으로 3년 이내 논문을 최우선으로 반영하되, 없으면 5년 이내 논문을 반영할 것. 초석이 되는 논문의 경우에는 년도 상관없이 반영 가능.
    - 환각을 방지하기 위해 반드시 교차 검증할 것.
    - 검증이 완료된 항목은 bibitem으로 사용할 수 있도록 json 파일로 관리할 것.
        - Journal: 모든 저자, 제목, 저널명, vol, no, pages, year, doi 등과 해당 논문에 대해 3문장 정도의 요약
        - Conference: 모든 저자, 제목, 학회명, 위치, pages, year, doi 등과 해당 논문에 대해 3문장 정도의 요약
 (5) visualizer
    - 성능평가에 표기할 비교 방안 및 제안 방안의 이름, 색상, 순서를 꼭 지킬것.
    - 그래프의 제목 제거 (추후 논문에 caption으로 넣을 것이기 때문)
    - 그래프의 축, 라벨, 범례, 폰트 크기 등이 논문에 들어가기 적합하도록 학술적이고 일관된 톤을 유지할 것.
    - 동일한 결과물은 덮어쓰기할 것.
        1. RGB(255,80,80) -> #FF5050
        2. RGB(237,125,49) -> #ED7D31
        3. RGB(255,153,102) -> #FF9966
        4. RGB(255,192,0) -> #FFC000
        5. RGB(204,204,0) -> #CCCC00
        6. RGB(112,173,71) -> #70AD47
        7. RGB(0,204,153) -> #00CC99
        8. RGB(51,153,255) -> #3399FF
        9. RGB(0,102,255) -> #0066FF
        10. RGB(102,102,255) -> #6666FF
        11. RGB(204,102,255) -> #CC66FF
        12. RGB(255,102,255) -> #FF66FF
        13. RGB(255,0,0) -> #FF0000
 (6) worker: 파일의 이동 및 복사 등의 간단 작업으로 가장 낮은 모델 사용
 (7) writer
    - LaTeX 또는 Markdown 포맷으로 논문의 구체적인 섹션 드래프트를 작성하며 학술적 문체를 유지할 것.
    - AI적 표현 금지.
    * 과장된 단어
    * 과도한 부사
    * 과도한 문장 기호 표현 --- ---, *** ***, - -, :, ;
    * 불필요한 괄호 사용. (소괄호는 축약어를 처음에 설명할 때 한 번이면 됨.)
    * 문단 길이는 최소 5문장 이상으로 할 것.
    * 리스트 남용 검증할 것. itemize와 enumerate를 지시하지 않는 이상 산문으로 풀어 쓸 것.
    * 등
    
 전체 룰: 수정 후 검토자에게 완벽에 대한 승인을 받을 때까지 반복 수정. 애매한 부분의 경우 임의 실행 금지하며 사용자에게 물어볼 것. 결과물은 항상 최신 버전만 유지하며 이전 버전은 백업할 것.

   /grill-me : 애매한 거는 사용자에게 전부 질문하여 픽스하기
   /plan : 진행하지 않고 일단 계획서를 만들어 사용자에게 컨펌받기
   /teamwork-preview : orchestrator가 되어 하위 에이전트 팀을 꾸려 대형 프로젝트 진행
   /learn : 사용자와의 피드백을 기반으로 자체적인 업그레이드
   /resume : 세션을 불러오기
   /rename : 세션의 이름을 바꾸기
   /clear : 이 세션을 접고 정리하기
   /btw : 현재 진행 중인 것들은 놔두고 병렬적으로 질의응답을 진행
   /goal : 목표에 달성하기 위해 여러번에 걸쳐서 작업을 수행하여 목표에 도달할 때까지 무한 진행
   /usage : 토큰 사용량과 잔량 확인 (주간당, 5시간당 사용량 확인)
   /exit : 안티그래비티 종료
   /model : 세션 모델 변경

## 1. 대략적인 아이디어 설정
어떤 환경에서 무엇을 하기 위한 어떤 방안인지는 대략적으로 가져가는 것이 맞다.
추후 그 큰 틀이 바뀌더라도 일단은 대략적으로 가지고 있어야 논문 탐색에 용이하기 때문이다.
단순하게 "내가 논문 필요한데 논문 쓰기 위한 작업해줘."라고 하면 너무 광범위한 범위로 인해 힘들어지기 때문이다.
만약 연구 분야를 정하지 못 했다면 그것도 상관없다.
관심있는 또는 연구를 하고 싶은 분야를 말해주며 최신 년도와 같이 요즘 해당 연구 분야의 트랜드를 조사해달라고 하면 된다.
이때 꼭 유의할 것이 있다:
    (1) 최신 년도는 20xx 형식으로 꼭 숫자로 써주어야 한다. AI는 자기가 학습된 시점을 최신으로 알기 때문에 현재 기준 2024년을 퇴신으로 인지하기 때문이다.
    (2) 찾은 논문은 다시 Web으로 접근하거나 환각을 일으킬 수 있기 때문에, DOI로 검증을 하도록 하고 논문의 인용에 필요한 정확한 정보를 JSON 파일로 저장시켜야 한다.
    (3) 또한, IEEE 등 많은 논문지에서 너무 빠르고 잦은 논문 검색 요청을 서버 과부하의 이유로 거부한다. 그러고 24시간의 대기 시간을 주어 탐색을 멈추게 한다. 그러나 IEEE는 1초에 1편의 검색에 대해서 가능하도록 풀어놓았다. 심지어 IEEE의 논문 검색에 대한 API KEY를 받아서 운용하면 그 1초에 1편 검색에 대한 신뢰성을 보장받게 된다. 따라서, 어떤 방향이든 24시간, 20시간, 5시간 등의 긴 시간에 대한 대기를 받는다면, 10초 후 다시 검색해보고 5번 연속으로 실패하면 멈추게 한 뒤 다시하는 것이 좋다.

대략적이거나 구체적인 아이디어가 있다면 그것을 상세히 설명한다.
글이 너무 길어질 것 같으면, 모델을 더 상위 모델로 활용하도록 하고, md 파일로 작성하여 읽게 하는 것도 방법이다.
그리고, 해당 Workspace에 idea 디렉토리를 만들어서 앞으로도 계속 수정될 수 있는 아이디어의 버전을 관리하게 하는 것도 좋다.
그리고 오래되고 사용되지 않을 파일에 대해서는 너무 많이 쌓일 수 있기 때문에 backup 디렉토리에 넣어두라고 하는 지시도 필요하다.

이때도 똑같이 DOI로 검증하도록 시키고 JSON 파일로 저장시키도록 지시한다.

    (1) 최신의 논문 3개
    (2) 가장 유사한 논문 3개
    (3) 기본 방안 3개
 이외에도 사용하기 좋은 논문들은 JSON 파일로 저장하게 하여 나중에 Related Works에 사용하기 좋게 한다.

## 3. 시뮬레이션 설계
시뮬레이션이 돌아가기 위해서는 정확한 환경이 필요하다. 노드들의 특징은 무엇인지, 어디에 있는지, 이동을 하는지 등 매우 자세히 설명할 수록 시뮬레이션의 정확도가 올라간다.
(1) 환경 설명: 예를 들어 차량 네트워크 상황이면, 도로가 몇 차선으로 이루어져 있고, 교차로가 어디에 있고, 얼만큼 떨어져 있고, 신호등이 있는지 등을 설명한다.
(2) 노드 설명: 통신 논문이기 때문에, 통신을 하는 주체들의 설명이 필수적이다. 어떤 이동성, HW, SW 적인 특징이 있는지 전부 설명할 필요가 있다.
(3) 통신 모듈 설명: 만약 타겟으로 하는 Layer가 있다면 나머지 부분까지 모두 구현할 필요는 없을 것이다. 따라서, 나머지 Layer에 대해서는 표준화된 기능이 구현될 필요가 있다. 해당 분야에서 자주 사용되는 통신 모듈을 찾아내어 구현하도록 지시한다.
(4) ML 설명: 딱히 제안 방안이 없고 별도의 지시가 필요없다면 언급하지 않아도 좋다.
모든 코드가 다 완성이 되었을 때, 믿고 바로 진행하면 안됀다.
환각으로 인해 코드 중간중간이 구현이 안되어 있거나 테스트 버전으로 구현되어 있을 확률이 높다.
해당 세션과 다른 세션, 다른 AI를 통해 검증을 받는다.
검토된 내용을 MD 파일 보고서로 정리하도록 시키고 그것을 수정하도록 시킨다.
계속 수정해 나가면서 AI가 이젠 완벽하다고 이야기가 나올 때까지는 적어도 돌아가야 시뮬레이션의 신뢰도가 비약적으로 상승한다.
물론, 해당 과정에서 상당한 시간이 소요되게 되지만 나중에 전부 뜯어 고치는 불상사를 방지하기 위해선 필수 작업이다.

수정 요청을 할 때도 세심하게 요청하는 것이 좋다: 시뮬레이션을 다시 읽고 수정해줘: (1) 환경이 나와 결정한 사항에 대해 제대로 반영이 되었는지 확인. (2) 차량과 RSU 등의 노드가 제대로 구현되어 있는지 확인. (3) 통신 모듈이 충분히 현실적으로 구현되었는지 확인. (4) Baselines가 모두 제대로 구현되었는지 확인. (5) 기타 모든 코드 검토도 해볼 것

## 4. 비교 방안 성능 도출
(1) HyperParameter Optimization (HPO)
ML 방안이라면 우선 optuna를 통해서 각 방안에 맞게 하이퍼파라미터를 조정할 필요가 있다.
엉망진창인 하이퍼파라미터를 사용하여 성능을 비교하면 아무리 좋은 최신 모델이라고 해도 성능이 떨어져서 제대로 된 공정한 비교가 아니게 되기 때문이다.
이때도 그냥 optuna로 각 비교 방안의 하이퍼파라미터를 최적화해 달라고만 하면, Learning Rate나 batch size 등의 기초적인 공통 하이퍼파라미터만 최적화하게 된다.
따라서, 약간의 예시를 주며 각 방안에 적절한 하이퍼파라미터들을 선택하여 최적화해달라고 하면 된다.
그러기에 가장 좋은 방법은 각 방안에 핵심이 될만한 하이퍼 파라미터를 csv 파일로 정리시키는 방법이다.
그 후 해당 csv 파일을 읽게 하여 각 방안에 맞는 하이퍼파라미터들을 optuna로 최적화해달라고 하면 된다.

(2) 비교 방안 성능평가
제안 방안이 어떤 구조나 아이디어를 채용할지 모르기 때문에 구체적인 성능지표를 골라놓을 수는 없어도 기본적인 성능은 도출할 수 있다.
ML 이라면 가장 좋은 방법은 SL의 경우 MAE, MAPE, R2 Score 등의 정확도나 RL의 경우 Reward값이 될 것이다.
그리고, 통신 관련 성능도 미리 설계해두면 좋다. 예를 들면, CBR, AoI, Delay, Traffic 등이 있다.
그래서 비교 방안들의 성능을 먼저 뽑고 제안 방안을 거기에 비교해 가면서 개발할테니 비교 방안들의 정해진 성능을 평가하기 위한 코드를 구현해달라고 하면 코드가 구현되기 시작할 것이다.
물론, 성능을 평가한 지표는 CSV 파일로 저장하게 하여 보다 확실한 결과물을 저장해 놓는다.
특히, Learning curve를 그릴테니 그 부분에 대한 기록은 꼭 남겨두도록 시킨다.

또한, HPO가 수행된 뒤 학습이 완료된 모델 또한 저장해두라고 한다. 추후 통신 성능이든 다른 성능 등을 비교하기 위해서 또 다시 학습을 시키는 번거로움을 줄이기 위해서다.
마지막으로, 중간에 컴퓨터가 비정상적인 종료되는 경우 많은 데이터가 날아갈 수 있기 때문에, 이를 유의시키고 중간에 OFF 되어도 이어서 실행할 수 있도록 조치를 취하도록 지시한다.
몇날 몇일에 걸쳐서 비교 방안들이 하나씩 학습되며 평가된다.
이 부분에서 엄청 많은 시간이 소요된다.
하지만, 돌아가고 있는 동안 사용자는 자유롭기 때문에 다른 작업을 또 이어갈 수 있다.

## 5. 제안 방안의 개발
비교 방안들의 성능이 존재하며, 시뮬레이션이 존재하기 때문에 제안 방안은 ML 디자인만 하면 된다.
만일 패킷의 전달 방식이나 다른 부분에 대한 방안이어도 어차피 지시만 잘하면 문제 없다.
단, 기존에 완성된 코드는 무조건적으로 살릴 필요가 있다.
기존의 코드로 도출된 비교 방안의 성능을 사용할 것이기 때문에, 새로운 파일로 코드를 작성 및 수정하도록 지시한다.
그냥 다양한 방법으로 최적의 방안을 찾아달라고 하면, 2024년 기준이면서 엄청 단순한 방안들부터 고려하게 된다.
예를 들면, PPO에 무엇을 붙인다던지 하는 식이다.
요즘은 TD3도 나왔고, 적어도 PPO 보단 SAC가 성능이 더 잘나온다. 심지어 MAPPO도 나왔다.
따라서, 내부 네트워크에 ResNet을 심어본다던지, ResBlock을 심어본다던지, CVAE 구조를 심는다던지, feature를 더 categorize 해본다던지 등의 예시를 건네주면 더 다채롭게 시도를 하기 시작한다.
상황에 따라서는 여기서 시간이 이전보다 더 걸릴 수도 있다.
더 좋은 방안을 찾기가 힘든 구조 였다면, 2달 동안 New Idea만 찾으며 돌아가는 경우도 있다.
그래도 언젠간 비교 성능들을 능가하는 제안 방안의 설계를 성공하게 된다.

/goal baselines의 저장된 성능(R2 score, reward, delay, Traffic 등 사용자가 지정해줄것. 또는 모든 이라는 표현도 가능)을 뛰어넘는 제안 방안을 설계해야 해. 따라서, 내부 네트워크에 ResNet을 심어본다던지, ResBlock을 심어본다던지, CVAE 구조를 심는다던지, feature를 더 categorize 해본다던지 다양한 시도를 하여 찾도록 해. 단, 비교를 위해서는 각 시도마다 HPO는 필수로 하도록 해.

## 6. Contributions 정리
제안 방안을 찾아냈으면 가장 먼저 할 일은 그 모델이 왜 더 좋은지를 정리하는 일이다.
어떤 시도를 해보았고, 어떤 구조가 왜 좋은 성능을 내는지 원인을 분석시켜 정리한다.
그리고 그것을 idea에 저장하여 main contribution으로 설정한다.
해당 Contributions에 맞는 추가 성능 평가 그래프를 물어보고 성능 평가를 정리하기 시작한다.

## 7. 성능 평가 완료
ML이라면 기본적으로 Ablation Study, Sensitivity Analysis, Learning Curve는 있어야 한다.
Ablation Study는 하나씩 빼보면서 성능을 측정하여 그것이 제안 방안에 있어야 하는 정당성을 부여한다.
이 부분은 reward function 설계가 될 수도 있고, 구조 중에 어떤 block이 될수도 있고, 어떤 기법일수도 있다.
 - reward ablation study: proposed, w/o R1, w/o R2, ...
 - structure ablation study: proposed, w/o ResBlock, w/o CVAE, ...
필요한 부분에 있어서 진행하도록 한다.
이때, Bar 그래프로 표현이 되기도 하는데, 이왕이면, 학습에 있어서도 어떤 특징을 나타내는지 보여줄 수 있도록 Learning curves로 그려달라고 하는 것이 좋다.

구조에 대한 정당성이 검증이 되면 하이퍼파라미터를 최적화하기 위해 Sensitivity Analysis를 해야하지만 요즘엔 Optuna라고 하는 좋은 라이브러리가 있으니 사용하도록 한다.
논문에는 Optuna를 통해서 찾은 최적의 하이퍼파라미터가 무엇인지 적어주면 된다.

그러면 모델이 돌아가기 위한 설정이 완료되었기 때문에 학습이 남게 된다.
그전에 이미 기록을 해둔 csv가 있다면 그대로 사용하면 된다.
모든 비교 방안들과 제안 방안의 learning curves를 하나의 그래프에 담아서 특징을 비교한다.
수렴이 빠른지, 최댓값이 높은지, 안정적인지를 주로 보면 된다.
만일 여기서 제안 방안이 안 좋은 성능이 나온다면, 몇번의 다양한 시도를 하다가 결국 5. 로 돌아가게 된다.

여기서 비정상적인 수치 혹은 너무 이상적인 수치가 나올 수도 있다.
그 경우엔 최악인 상태다.
시뮬레이션부터 해서 모든 것을 의심해봐야 한다.
다른 AI의 고급 모델을 통해 코드를 전수 조사해야 하며 3. 으로 돌아간다. 더 최악인 경우, 비교 방안의 논문이 가짜로 밝혀지며 2. 로 돌아갈 수도 있음을 염두해두자.

그리고 Contributions을 검증하기 위한 다양항 성능 평가 그래프 또는 테이블을 제시한다.

그리고 나서는 이렇게 좋은 우리 방안이 현실적으로 돌아갈 수 있는지를 보여주기 위해 Hardware Feasibility를 테이블로 뽑는다.
GPU, CPU, RAM 사용량, 하이퍼파라미터의 크기, 모델의 크기, FLOPs, 추론 시간, 학습 시간 등
그러고서 이 연산을 수행하는 주체가 누구인지 파악하여 해당 노드의 스펙을 얼추 작성할 필요가 있다.
차량인지, RSU인지, 기지국인지, 서버인지에 따라서 실제로 가능한 모델이냐가 판별된다.

마지막으로 현실적으로 가능하고 ML적으로 이렇게 좋은 모델이 통신에서 어떤 성능을 보이는지 보여줄 차례다.
여기서 X축은 어떤 것들을 바꿔가며 뽑을 수 있는지 파악해본다.
예를 들면, 차량의 속도, 밀도, 기상의 상태 등 다양한 환경에서 이 모델이 Robust 한지를 검증하는 것이다.
이 성능 그래프 또한 다른 학습이 된 비교 방안들과 성능을 비교하는 그래프를 그리면 된다.
주로 X축의 변화에 따른 추이 그래프가 가장 선호된다.

## 8. 글 작업 시작
일단, 어떤 플랫폼에서 작성할지는 미리 알려주어야 한다.
Overleaf의 Latex 포맷으로 글을 작성할 것이라고 알려주고 시작하면 AI는 그 포맷으로 작성해준다.

1) Introduction
저자는 주로 4문단으로 고정하여 글을 작성했지만 요새는 서론이 짧아지는 추세이다.
그래도 문제제기-트랜드-제안방안의 흐름은 달라지지 않았다.
제안 방안의 Contributions가 잘 드러날 수 있도록 흐름에 맞추어 글을 작성하도록 시킨다.
그냥 시키게 되면, AI는 2~3문장의 문단만 만들게 된다.
5문장 이상이라고 명명하면 정말 5문장으로만 문단을 구성한다.
저자는 서론 정도는 직접 문장 단위로 어떤 내용이 어떤 순서로 들어가야 하는지 설계하는 것을 추천한다.
또한, 알맞은 위치에 적절한 논문을 찾아서 인용하도록 시키며 Reference에 해당 논문을 추가하도록 시키는 것도 필요하다.
그리고, itemize와 문단당 5문장 이상의 조건을 서론의 contribution 설명 문단에만 제외하여, 제안 방안의 contribution을 깔끔히 정리하는 것도 좋다.

2) Related Works
요즘은 이 섹션도 많이 짧아지는 추세다.
Table로 정리하여 한 눈에 보기 편하도록 작업하여 그런 것도 크다고 생각한다.
그만큼 기존 방안 또는 비교 방안들과 어떤 점이 다른지를 column으로 설정하는 것이 중요하다고 생각한다.
그렇더라고 이 분야가 어떻게 연구되어 왔는지는 순서대로 글을 흐름에 맞추어 서술할 필요가 있다.

3) Network Model
이 섹션에서는 다양한 방법의 서술이 존재한다.
여기서 MDP를 작성하기도 하고, 통신이나 계산/학습에 필요한 다양한 모듈을 설명하기도 한다.
Content Request Module, Trasmission Rate Management module 등

그러나, Overview에 대해서는 작성할 필요가 있다.
어떤 환경의 어떤 시나리오에 대한 내용인지 명확히 알려주어 이 방안에서 어떤 노드가 어떤 동작을 하는 시나리오인지를 확실히 알려줄 필요가 있다.
따라서, 개요도가 받쳐주면 논문이 한 층 풍성해진다.

즉, 여기서는 본문에 들어가기 앞서 필요한 사전 지식을 모두 설명하는 곳이다.

4) 본문
우리는 통신에 관련한 논문이기 때문에, 설명이 완전 ML에 치우치게 되면 근간이 흔들리게 된다.
따라서, 절차에 따라서 어떤 패킷이 또는 신호가 오고 가고, 그곳에는 어떤 정보가 들어있고, 어떤게 포워딩 되고 하는 흐름을 표현하는 것이 좋다.
그 안에서 어떤 정보가 어떻게 수집되는지, 어떻게 운용되는지, 그것이 어떻게 학습으로 이어지는지 등 세부적인 내용이 녹아들어가 있으면 된다.
단, 이 부분에 있어서도 크게 보았을 때 서론에 작성한 Contributions가 드러나도록 흐름이 있어야 할 것이다.

5) 성능평가
이 섹션의 시작은 시뮬레이션 또는 실험 환경이다.
어떤 환경에서 실험이 되었는지 다른 사람이 보아도 그대로 구현할 수 있을 정도로 구체적으로 적어주면 좋다.

그 후 비교 방안들을 설명한다.
비교 방안들을 증빙하기 위한 논문과 구현하기 위한 github 링크 등을 인용하는 것이 좋다.
아니라면 하나씩 설명을 해야할 것이다.

그 후 어떤 평가 지표들이 있는지 정리해서 알려준다.
어떤 지표가 있고 그것은 무엇을 의미하는지 등을 알려준다.
예: Access delay는 RSU가 서버로 까지 패킷을 보내서 content를 받아오기 위한 delay로서 서버로의 접근이 얼마나 잦았는지 또는 절약했는지를 표현한다.

그 후 성능 평가는 위의 순서에 따라서 하나씩 나열되며 설명된다.

6) 결론 & 요약
