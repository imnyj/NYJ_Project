# 논문 작업 Walkthrough

이 문서는 새 논문 프로젝트(paper1, paper3, paper5 등)를 진행할 때 Claude 에게 건네는 작업 안내서의 입구 파일입니다.
사용자의 논문 작업 방식(`NYJ_Paper_Prompt.md`, `논문 명령어.md`)과 성능 그래프 구성, 논문 작성 요령(`/home/imnyj/command.md`)을 단계 순서대로 정리했으며, 단계별 세부 절차는
`paper_walkthrough/` 폴더의 파일에 나누어 두었습니다. 한 파일에 모든 절차를 담으면 매 단계마다 필요 없는 내용까지 읽게 되고,
여러 세션에 걸친 작업에서 현재 단계만 다시 읽기 어렵기 때문입니다.

## 1. 사용법

사용자는 새 프로젝트를 시작할 때 이 파일의 경로를 건네고 진행을 지시합니다.

> /home/imnyj/정리/Private/paper_walkthrough.md 를 읽고 paper5 에서 논문 작업을 진행해. 대략적인 아이디어는 다음과 같아. ...

이미 진행 중인 프로젝트를 이어 갈 때는 다음처럼 지시합니다.

> /home/imnyj/정리/Private/paper_walkthrough.md 를 읽고 paper5 의 WALKTHROUGH_STATE.md 에서 멈춘 단계부터 이어서 진행해.

## 2. Claude 가 지킬 진행 방식

1. 이 파일을 끝까지 읽은 뒤, 현재 단계에 해당하는 단계 파일만 읽습니다. 모든 단계 파일을 한 번에 읽지 않습니다.
   단계 파일이 다른 단계 파일을 참조하면 참조한 절만 추가로 읽습니다.
2. 프로젝트 루트(`/home/imnyj/Workspace/paperN/`)에 `WALKTHROUGH_STATE.md` 를 만들고(양식은 7절), 단계를 바꾸거나 사용자 결정을 받거나
   완료 조건을 통과할 때마다 갱신합니다. 새 세션이나 컨텍스트 압축 뒤에는 대화 기억이 아니라 이 파일부터 읽고 시작합니다.
3. 단계 파일의 **[사용자 결정]** 지점에 이르면 멈추고 AskUserQuestion 으로 묻습니다. 질문마다 선택지 2~4개와 각 선택의 결과 차이,
   추천안과 그 근거를 붙입니다. 사용자가 답하기 전에는 그 결정에 기대는 작업을 진행하지 않고, 결정과 무관한 준비 작업만 계속합니다.
   Claude 가 스스로 답을 정해 진행하지 않습니다.
4. 단계 파일의 **완료 조건**을 모두 만족하고 증거 파일이 실제로 있을 때만 다음 단계로 넘어갑니다. 넘어갈 때는 무엇을 근거로 통과했는지
   사용자에게 짧게 보고합니다.
5. 단계 파일의 **되돌아가기 조건**에 해당하는 상황이 생기면, 진행을 멈추고 증거와 함께 사용자에게 알린 뒤 되돌아갈 단계를 확인받습니다.
6. 사용자가 단계 순서를 바꾸거나 단계를 건너뛰라고 하면 그 지시를 따르고, 건너뛴 단계와 이유를 상태 파일에 적습니다.

## 4. 흐름과 되돌아가기

```text
0 준비 → 1 아이디어 → 2 문헌·비교 방안 → 3 시뮬레이션 → 4 비교 방안 성능 → 5 제안 방안 → 6 Contributions → 7 성능 평가 → 8 원고
                                  ▲                ▲                                ▲                     │
                                  │                │                                └── 제안 방안 성능이 부족함 ┤
                                  │                └──────── 비정상적이거나 지나치게 이상적인 수치 ─────────────┤
                                  └──────────────────────── 비교 방안 논문이 가짜로 밝혀짐 ───────────────────┘
```

- 7단계에서 제안 방안의 성능이 기대에 못 미치면 몇 번 더 시도한 뒤 5단계로 돌아갑니다.
- 어느 단계에서든 비정상적이거나 지나치게 이상적인 수치가 나오면 가장 나쁜 상황으로 봅니다. 다른 AI 의 상위 모델까지 동원해 코드를 전수 조사하고 3단계로 돌아갑니다.
- 비교 방안의 근거 논문이 존재하지 않거나 내용이 다르다고 밝혀지면 2단계로 돌아갑니다.

## 5. 모든 단계에 공통으로 적용하는 규칙

이 워크스테이션의 전역 규칙(`~/.claude/CLAUDE.md`)과 `paper-team` 스킬이 우선합니다. 아래는 그중 논문 작업에서 특히 자주 쓰는 규칙입니다.

### 5.1 팀 운용

- 메인 세션은 오케스트레이터입니다. 코드 작성, 시뮬레이션 실행, 원고 작성 같은 실무는 직접 하지 않고 `pN-` 접두사를 붙인 7인 팀에게 맡긴 뒤 결과를 검증합니다.
  팀은 너무 많으면 방향이 흩어지므로 7인(coder, critic, idea, librarian, visualizer, worker, writer)으로 고정합니다.
- 결과물은 검토자(critic)에게 "더 고칠 것이 없다" 는 승인을 받을 때까지 반복해서 고칩니다. 검토자는 직접 고치지 않고 수정 지침만 냅니다.
- 서브에이전트는 모호한 부분을 추측으로 채우지 않고 보고서 맨 위 `## 질의` 블록에 적어 멈춥니다. 오케스트레이터는 그 질의를 AskUserQuestion 으로 사용자에게 올리고,
  답을 SendMessage 로 해당 서브에이전트에게 전달합니다. 오케스트레이터가 답을 지어내지 않습니다.
- 같은 파일을 건드리는 에이전트를 동시에 띄우지 않습니다.

### 5.2 기록과 환각 방지

- 모든 작업 자료는 파일(csv, md, json, npz 등)로 남기고, 필요할 때 다시 읽습니다. 대화 기억에 기대지 않습니다.
- 논문은 DOI 로 직접 조회해 검증한 것만 쓰고, 인용 정보는 JSON 으로 관리합니다. 확인하지 못한 수치와 문헌은 지어내지 않고 빈칸으로 두고 보고합니다.
- 실험 수치는 결과 CSV 를 직접 읽어 씁니다. 인수인계 문서나 기억 속 요약값을 옮기지 않습니다.
- AI 가 만든 코드는 중간중간 구현이 빠져 있거나 시험용으로 남아 있을 확률이 높습니다. 코드를 믿고 곧바로 진행하지 않고, 이 세션과 다른 세션, 다른 AI(Antigravity 등)로
  교차 검증합니다. Antigravity 의 완료 보고도 그대로 믿지 않고 코드와 결과를 직접 확인합니다.
- 최신 연도는 반드시 숫자로 씁니다(예: "2026년까지"). AI 는 자신이 학습된 시점을 최신으로 알기 때문입니다.

### 5.3 파일 관리

- 산출물은 `/home/imnyj/Workspace/paperN/` 아래에만 둡니다. 결과물은 최신본만 유지하고, 이전 판과 쓰지 않는 파일은 `backup/` 으로 옮깁니다.
- 보조 스크립트와 로그는 `etc/scripts/`, `etc/logs/`, `etc/temp/` 에 둡니다.
- 파일을 고칠 때는 `/home/imnyj/Command/core/lock_manager.py` 로 락을 잡고, Bash 로 고친 파일은 `audit_logger.py` 로 기록합니다(`workspace-protocol` 스킬).
- 같은 그래프 이미지는 덮어씁니다. 결과 CSV 나 원고처럼 판이 바뀌는 파일은 이전 판을 `backup/` 으로 옮긴 뒤 최신본만 남깁니다.

### 5.4 장시간 작업

- 수 시간 이상 걸리는 학습과 시뮬레이션은 세션과 분리된 프로세스로 돌리고, 체크포인트와 재개 기능을 갖춥니다. 컴퓨터가 비정상 종료되어도 이어서 실행할 수 있어야 합니다(`long-running-jobs` 스킬).
- RTX 3090 네 장에 작업을 나누어 싣습니다. 한 장에 몰지 않습니다.
- 장시간 본훈련은 시작 전에 사용자 승인을 받습니다.
- 진행 보고는 너무 잦으면 토큰만 소모하므로, 사용자가 따로 정하지 않았다면 6시, 12시, 18시, 24시에 한 번씩만 합니다. 디스코드를 연결했다면 디스코드로 보고합니다.
  정기 보고는 장시간 작업의 실행 래퍼가 해당 시각에 `dcbridge.py send` 로 보내게 하고, 에이전트가 시각을 기다리며 폴링하지 않습니다.
  세션과 분리된 래퍼에는 세션 정보가 없으므로, `--session-id <이 세션 ID>` 를 주어 그 세션의 봇과 스레드로 보내게 합니다. 세션 기록이 없다면
  `--profile <이 프로젝트의 봇 프로필> --label <라벨>` 을 지정합니다. 둘 다 빼면 기본 프로필의 봇으로 보내집니다.

### 5.5 승인이 필요한 작업

데이터 삭제, 대규모 파일 이동, 장시간 본훈련, 비용이 드는 API 사용, 외부 공개(GitHub 공개 등), git 커밋과 푸시는 실행 전에 사용자 승인을 받습니다.

### 5.6 사용자가 쓰는 명령

사용자는 진행 중에 아래 명령을 섞어 씁니다. Claude 는 이 명령이 오면 그 뜻에 맞게 동작합니다. `/resume`, `/rename`, `/clear` 는 Claude Code 에 내장된 명령이라
그대로 동작합니다. `/goal`, `/grill-me`, `/plan`, `/btw`, `/teamwork-preview`, `/learn` 은 원래 Antigravity 에서 쓰던 것이라 Claude Code 에는 스킬로 등록되어 있지
않을 수 있습니다. 이 명령이 인식되지 않으면 사용자는 슬래시 없이 같은 문장을 보내고, Claude 는 표의 뜻대로 동작합니다.

| 명령 | 뜻 |
|---|---|
| `/grill-me` | 애매한 부분을 사용자에게 모두 질문해 확정한다 |
| `/plan` | 진행하지 않고 계획서만 만들어 사용자 확인을 받는다 |
| `/goal` | 목표에 이를 때까지 여러 차례에 걸쳐 작업을 이어 간다 |
| `/btw` | 진행 중인 작업은 두고 병렬로 질의응답만 한다 |
| `/resume`, `/rename`, `/clear` | 세션을 불러오고, 이름을 바꾸고, 정리한다 |
| `/teamwork-preview` | 오케스트레이터가 되어 하위 에이전트 팀을 꾸려 큰 작업을 진행한다(5.1절의 팀 운용) |
| `/learn` | 사용자 피드백을 근거로 규칙과 스킬을 개선한다(`skill-crafter` 스킬) |

## 6. 사용자 결정 지점 한눈에 보기

아래 결정은 Claude 가 대신 내리지 않습니다. 해당 단계에 이르면 멈추고 묻습니다.

| 단계 | 결정할 사안 |
|---|---|
| 0 | 프로젝트 번호와 폴더 이름(알려 주지 않았을 때), 팀 규칙을 복제할 기존 프로젝트, worker 에 낮은 모델을 지정할지, 디스코드 연결과 보고 시각, 문헌 검색 재시도 간격 |
| 1 | 연구 분야와 시나리오, 최적화할 목표 지표, 트렌드 조사 뒤 택할 방향 |
| 2 | 비교 방안 최종 목록과 범주별 개수, 참신성 조사 뒤 아이디어 수정 여부 |
| 3 | 환경, 노드, 통신 계층과 표준 모듈의 세부값, `config.md` 기본값, 시뮬레이션 검증 통과 판단 |
| 4 | 평가 지표, 모델 순서와 색상, 방안별 핵심 하이퍼파라미터와 탐색 범위, 학습 step 수, 본훈련 시작 |
| 5 | 넘어야 할 지표와 기준, 시도 방향의 우선순위, 탐색을 멈출 시점, 최종 제안 방안 확정 |
| 6 | Contributions 확정, 성능 평가 그래프의 흐름과 개수, 서론 문장 설계 |
| 7 | ablation 대상, Sensitivity analysis 를 보일 형태, 환경 변화 실험의 X축 변수와 범위와 Y축 성능, 연산 주체 노드, 그래프 해석 확정 |
| 8 | 대상 저널과 분량, Related Works 표의 비교 열, 코드 공개 범위와 저장소 이름, 저자·소속·연구비 정보 |

## 7. WALKTHROUGH_STATE.md 양식

0단계에서 아래 양식으로 만들고, 이후 모든 단계에서 갱신합니다.

```markdown

- 안내서: /home/imnyj/정리/Private/paper_walkthrough.md
- 현재 단계: 3 (시뮬레이션) — 진행 중
- 마지막 갱신: 2026-09-12 14:00

## 완료한 단계
| 단계 | 완료 일시 | 통과 근거(파일 경로) |

## 사용자 결정 기록

|---|---|---|---|

## 대기 중인 질문
(없으면 "없음")

## 되돌아가기 기록
(없으면 "없음")

## 다음 행동
- ...
```
