# 3단계. 시뮬레이션 설계와 검증

## 목적

제안 방안과 비교 방안을 공정하게 평가할 시뮬레이션을 만들고, 믿을 수 있을 때까지 검증합니다. 환경을 자세히 설명할수록 시뮬레이션의
정확도가 올라갑니다. 이 단계의 검증은 시간이 오래 걸리지만, 나중에 전부 뜯어고치는 일을 막기 위해 반드시 거칩니다.

## 들어가기 전 조건

- 1단계의 `sketch.md` 와 2단계의 `comparative_methods.md` 가 있습니다.

## 참여 역할

coder(구현), critic(검증), idea(설계 일치 확인), worker(보고서 기록)

## 절차

1. **[사용자 결정]** 아래 네 가지 설명을 사용자에게 받아 `simulation_plan.md` 로 정리합니다. 빠진 값은 추측하지 않고 묻습니다.
   - 환경: 예를 들어 차량 네트워크라면 도로가 몇 차선인지, 교차로가 어디에 얼마나 떨어져 있는지, 신호등이 있는지 적습니다. SUMO 같은 도구의 파일을 쓴다면 그 경로와 설정값을 적습니다.
   - 노드: 통신하는 주체마다 이동성, 하드웨어, 소프트웨어 특징을 모두 적습니다.
   - 통신 모듈: 대상 계층이 있다면 나머지 계층은 모두 새로 만들 필요 없이, 그 분야에서 자주 쓰는 표준 모듈을 찾아 구현합니다.
   - ML: 제안 방안이 아직 없거나 따로 지시할 것이 없다면 비워 둡니다.
2. 사용자가 환경 변수를 쉽게 바꿀 수 있도록 `config.md` 를 두고, 코드가 이 파일에서 값을 읽게 합니다. 특별한 값의 뜻(예: 차량 속도나 밀도가 0 이면 무작위)을 파일에 적습니다.
   **[사용자 결정]** `config.md` 의 기본값을 확인받습니다.
3. coder 가 `code/` 에 구현합니다. 여러 사용자가 비동기로 다음 상태에 이르는 시나리오라면 step 단위로 움직이는 Env 대신 for 문 기반의 시뮬레이션 루프로 구현합니다.
4. 코드가 완성되어도 곧바로 믿지 않습니다. critic 이 아래 다섯 항목을 검토해 보고서를 쓰고(worker 가 `review/` 에 기록), coder 가 고치는 과정을 critic 이 "더 고칠 것이 없다" 고 할 때까지 반복합니다.
   - (1) 환경이 사용자와 결정한 사항대로 반영되었는가
   - (2) 차량, RSU 같은 노드가 제대로 구현되었는가
   - (3) 통신 모듈이 충분히 현실적으로 구현되었는가
   - (4) 비교 방안(baselines)이 모두 제대로 구현되었는가
   - (5) 그 밖의 모든 코드: 구현이 빠진 곳, `TODO` 나 `pass` 로 남은 곳, 시험용 가짜 구현, 데이터 누수, 환경과 모델의 객체 타입
5. 같은 세션의 검토만으로 끝내지 않습니다. 다른 세션이나 다른 AI(Antigravity 등)에게도 코드를 검토하게 하고, 그 결과도 보고서로 남겨 반영합니다.
6. coder 가 단위 테스트와 검증 스크립트를 실행해 결과를 `etc/logs/` 에 남깁니다.
7. **[사용자 결정]** 검토 보고서들과 테스트 결과를 요약해 보여 주고 시뮬레이션 검증 통과 여부를 확인받습니다.

## 산출물

- `simulation_plan.md`, `config.md`, `code/` 의 시뮬레이션 코드
- `review/` 의 critic 검토 보고서와 교차 검토 보고서, `etc/logs/` 의 테스트 로그

## 완료 조건

- critic 의 마지막 보고서가 "더 고칠 것 없음" 이고, 교차 검토에서 나온 지적이 모두 반영되었습니다.
- 단위 테스트가 통과했고, 사용자가 통과를 확인했습니다.

## 되돌아가기 조건

- 이후 단계에서 비정상적이거나 지나치게 이상적인 수치가 나오면 이 단계로 돌아와 시뮬레이션부터 전부 의심하고 다시 검증합니다.

## 사용자 명령 예시

> 시뮬레이션을 다시 읽고 수정해줘: (1) 환경이 나와 결정한 사항에 대해 제대로 반영이 되었는지 확인. (2) 차량과 RSU 등의 노드가 제대로 구현되어 있는지 확인.
> (3) 통신 모듈이 충분히 현실적으로 구현되었는지 확인. (4) Baselines 가 모두 제대로 구현되었는지 확인. (5) 기타 모든 코드 검토도 해볼 것.

> 시뮬레이션의 신뢰성부터 확보하고 싶어. coder 에게 코딩을 맡기고, critic 에게 검증을 맡기고, 고칠 것이 없을 때까지 구현을 계속 반복하도록 해.
> 1) sumo 파일을 기반으로 한 네트워크 환경 세팅 검증. 사용자가 편하게 환경변수 세팅을 변경할 수 있도록 config.md 운용할 것. 차량 속도나 밀도 = 0은 랜덤 설정.
> 2) 통신 모듈 구현 검증 3) 비교 모델들의 구현 검증 4) 제안 모델의 구현 검증

두 번째 예시의 "4) 제안 모델의 구현 검증" 은 제안 방안이 생긴 뒤인 7단계 절차 1에서 합니다. 3단계에서는 1)부터 3)까지만 진행합니다.
