# 7단계. 성능 평가 완료

## 목적

6단계의 그래프 목록대로 성능 평가를 모두 수행합니다. ML 방안이라면 Ablation Study, 하이퍼파라미터 결정 근거, Learning Curve 가 기본이고,
여기에 contribution 을 검증하는 그래프와 표, 하드웨어 실현 가능성, 환경 변화에 대한 강건성 평가를 더합니다.

## 들어가기 전 조건

- 6단계에서 승인받은 `figure_list.md` 와 `visualizer/config.md`(모델 순서와 색상)가 있습니다.

## 참여 역할

coder(실험과 플롯 구현), critic(수치와 그래프 검증), visualizer(그래프 규격과 지시), worker(파일 정리)

## 공통 규칙

- 모든 그래프는 raw data 를 실제로 뽑아 CSV 로 관리한 뒤 그 CSV 에서 그립니다. 시간이 오래 걸려도 추정값이나 가짜 데이터로 그리지 않습니다.
- 구현은 coder 가 맡고 검증은 critic 이 맡아, 더 고칠 것이 없을 때까지 반복합니다. visualizer 는 그래프를 그릴 때만 참여해 규격을 지시하고, 코드는 coder 가 씁니다.
- 그래프에는 제목을 넣지 않습니다(논문에서 caption 으로 처리). 모델 순서와 색상은 `visualizer/config.md` 를 따르고, 같은 그래프는 덮어씁니다.

## 성능 결과 구성

사용자가 논문에 싣는 성능 결과는 아래 세 묶음입니다. `figure_list.md` 도 이 묶음으로 나누어 적고, 논문의 성능 평가 절도 이 순서를 기본으로 합니다.

| 묶음 | 결과 | 보여 줄 것 | 절차 |
|---|---|---|---|
| 1. ML 공통 결과 | State/Feature ablation | state 나 feature 의 구조 설계가 타당함 | 2 |
| | Reward/Loss ablation | 강화 학습의 reward function, 또는 지도 학습에서 직접 설계한 loss function 이 타당함 | 2 |
| | Structure ablation | 모델의 내부 구조나 추가한 기법이 각각 필요함 | 2 |
| | Sensitivity analysis | optuna 로 결정한 제안 방안의 하이퍼파라미터가 타당함 | 3 |
| | Learning curves | 제안 방안이 모든 비교 방안보다 빨리 수렴하거나 더 높은 성능으로 수렴함 | 6 |
| | Hardware feasibility | 서버, 기지국, 단말기 같은 실행 주체에서 돌아갈 수 있는 사양임 | 9 |
| 2. Contributions 에 따른 결과 | contribution 마다 하나 이상 | 무엇 때문에 무엇이 좋아졌는지 | 8 |
| 3. 연구 분야의 주요 결과 | 환경 변화에 따른 추이 | X축: 사용자 밀도, 속도 같은 환경 변화 변수. Y축: Delay, Traffic, AoI 처럼 논문이 목표로 하는 성능이나 부가적으로 달성하는 성능 | 4, 5, 10 |

시간 흐름에 따른 지표 그래프(절차 4, 5의 PDR, CBR, AoI 등)는 셋째 묶음에 X축을 시간으로 둔 결과로 넣습니다. 이 가운데 논문에 싣지 않을 결과가 있으면
6단계의 그래프 목록 결정에서 사용자가 정합니다.

## 절차

1. 시뮬레이션의 신뢰성을 다시 확인합니다. 3단계 이후 코드가 바뀌었다면 3단계의 다섯 항목 검토를 다시 거칩니다. 제안 모델의 구현 검증도 이때 같은 기준으로 합니다.
2. Ablation Study 로 각 설계 요소가 제안 방안에 있어야 할 정당성을 보입니다. 하나씩 빼 보며 성능을 잽니다. **[사용자 결정]** 어떤 ablation 을 할지 확인받습니다.
   - State/Feature ablation: state 나 feature 의 구조 설계를 검증합니다.
   - Reward/Loss ablation: 강화 학습이면 reward function 을, 지도 학습에서 loss function 을 직접 설계했다면 loss function 을 검증합니다(예: proposed, w/o R1, w/o R2, ...).
   - Structure ablation: 모델의 내부 구조나 추가한 기법을 하나씩 빼며 검증합니다(예: proposed, w/o ResBlock, w/o CVAE, ... 또는 ResNet+MoE+Dueling, w/o ResNet, w/o MoE, w/o Dueling).
   막대 그래프로 끝내지 말고, 학습 과정의 특징도 보이도록 학습 곡선으로도 그립니다.
3. 구조의 정당성이 검증되면 하이퍼파라미터를 정합니다. 예전처럼 하이퍼파라미터를 하나씩 바꿔 가며 찾는 대신 optuna 로 최적값을 찾고, 최적값을
   `data/hpo/proposed_best_params.csv` 에 저장합니다. Sensitivity analysis 결과로는 optuna 로 결정한 제안 방안의 하이퍼파라미터들을 보이며, 논문에는 optuna 로 찾은
   최적값을 적습니다. **[사용자 결정]** 최적값 표만 실을지, optuna 탐색 기록에서 하이퍼파라미터별 성능 변화 그래프도 뽑을지 확인받습니다.
4. 비교 방안의 데이터부터 확정합니다. 4단계의 `data/hpo/best_params.csv` 와 수렴 모델이 있으면 HPO 와 학습을 다시 돌리지 않고 그대로 씁니다.
   코드가 바뀌어 다시 돌려야 하면 먼저 사용자에게 묻습니다.
   - 모델별 reward 수렴: 상승 후 수렴하는 지점까지 뽑습니다(경험상 20만 step 이상). 4단계의 기록이 있으면 그대로 씁니다.
   - 저장한 수렴 모델로 시간 흐름에 따른 성능 지표(PDR, CBR, AoI 등)를 뽑습니다.
   - 환경 파라미터(차량 수, 차량 속도 등)를 바꿔 가며 시간 흐름에 따른 성능 변화를 뽑습니다.
5. 제안 방안의 데이터를 같은 방식으로 수집합니다.
6. 모든 비교 방안과 제안 방안의 학습 곡선을 한 그래프에 담아 수렴 속도, 최댓값, 안정성을 비교합니다. 이 그래프로 제안 방안이 모든 비교 방안보다 빨리 수렴하거나
   더 높은 성능으로 수렴함을 보입니다.
7. 수집한 데이터로 그래프를 하나씩 그립니다. 그래프마다 파일 경로와 요지를 보고하고 다음 그래프로 넘어갑니다. 사용자가 수정을 요청하면 그때 고칩니다.
8. contribution 을 검증하는 그래프와 표를 그립니다. MoE routing 이나 t-SNE clustering 처럼 해석이 필요한 그래프는 데이터를 근거로 그 뜻을 분석해 `review/figure_notes.md` 에 적고,
   **[사용자 결정]** 해석을 확인받습니다.
9. 하드웨어 실현 가능성 표를 만듭니다. GPU, CPU, RAM 사용량, 하이퍼파라미터 규모, 모델 크기, FLOPs, 추론 시간, 학습 시간을 잽니다.
   **[사용자 결정]** 이 연산을 실제로 수행할 주체(차량, RSU, 기지국, 서버)를 확인받고, 그 노드의 대략적인 사양과 비교해 실현 가능성을 판단합니다.
10. 통신 성능의 강건성을 보입니다. **[사용자 결정]** X축으로 바꿀 변수와 범위(사용자나 차량의 밀도, 속도, 기상 상태 등)와 Y축에 둘 성능을 정합니다.
    Y축은 논문이 목표로 하는 성능(Delay, Traffic, AoI 등)이나 부가적으로 달성하는 성능입니다. 학습된 비교 방안들과 함께 X축 변화에 따른 추이 그래프로 그리는 형태를 가장 선호합니다.

## 산출물

- ablation, 학습 곡선, 시간 흐름 지표, 환경 변화 실험의 CSV 와 그래프
- `data/hpo/proposed_best_params.csv`, 하드웨어 실현 가능성 표, `review/figure_notes.md`

## 완료 조건

- `figure_list.md` 의 모든 항목에 CSV 와 그래프가 있고, critic 이 수치를 CSV 와 대조해 확인했습니다.
- 그래프에 제목이 없고, 모델 순서와 색상이 `visualizer/config.md` 와 일치합니다.

## 되돌아가기 조건

- 제안 방안의 성능이 좋지 않으면 몇 번 더 시도한 뒤 5단계로 돌아갑니다.
- 비정상적이거나 지나치게 이상적인 수치가 나오면 가장 나쁜 상황으로 봅니다. 다른 AI 의 상위 모델로 코드를 전수 조사하고 3단계로 돌아갑니다.
- 비교 방안의 근거 논문이 가짜로 밝혀지면 2단계로 돌아갑니다.

## 사용자 명령 예시

> 성능 평가 구현의 순서는 다음과 같이 가도록 하자. coder 에게 구현을 맡기고, critic 에게 검증을 맡겨서 더 고칠 것이 없을 때까지 반복하도록 해.
> 그래프를 그릴 때만 visualizer 의 개입을 열도록 해. 시간이 오래 걸리더라도 Raw data 를 뽑아서 실제 성능을 뽑아 csv 로 관리하자.
> 1) 구조의 ablation study 2) reward 의 ablation study 3) state 에 대한 ablation study 4) optuna 로 최적의 하이퍼파라미터를 csv 로 저장
> 5) 비교 방안 전체에 대한 optuna 최적화 진행 6) 비교 방안들부터 데이터 fix 7) 제안 방안 데이터 수집 8) 수집된 데이터들을 기반으로 그래프 하나씩 그려보기
